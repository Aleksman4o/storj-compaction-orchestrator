# Массовое добавление и экспорт нод

## Импорт через интерфейс

На вкладке «Настройки» в разделе «Все ноды» нажмите «Импорт». Окно принимает
два формата:

- строки `ИМЯ URL MULTINODE_KEY ДИСК [true|false]`, по одной ноде на
  строку;
- JSON-массив нод или объект с массивом `nodes`.

Импорт сначала добавляет ноды только в открытую форму. Проверьте результат и
нажмите общую кнопку «Сохранить изменения». Если хотя бы одна строка
некорректна или повторяет существующий dashboard-адрес, не будет добавлена вся
партия.

Кнопка «Экспорт» скачивает JSON со списком дисков и нод. Multinode keys в него
не включаются и остаются только в SQLite на backend. Пустые поля `apiKey` можно
заполнить вручную, после чего массив `nodes` подходит для импорта в другой
экземпляр с такими же идентификаторами групп дисков.

## Импорт непосредственно через API

Отдельного API endpoint для импорта нет. Ноды можно добавить одной атомарной
операцией: получить полный документ настроек, дописать в него новые ноды и
отправить весь документ обратно.

> [!WARNING]
> `PUT /api/settings` заменяет документ настроек целиком. Всегда начинайте со
> свежего ответа `GET /api/settings` и сохраняйте из него массивы `groups`,
> существующих `nodes` и `schedules`.

В примерах используются стандартные локальный адрес и пароль оркестратора.
Измените их, если оркестратор запущен с другими параметрами.

## Что понадобится

- `curl`;
- `jq`;
- multinode API key для каждой новой ноды;
- существующая в оркестраторе группа физического диска для каждой новой ноды.

Задайте адрес оркестратора и путь временного файла cookie:

```bash
ORCHESTRATOR_URL=http://127.0.0.1:14008
COOKIE_FILE=/tmp/storj-orchestrator-cookie
```

## 1. Авторизация

```bash
curl -fsS \
  -c "$COOKIE_FILE" \
  -H 'Content-Type: application/json' \
  -d '{"password":"orchestra"}' \
  "$ORCHESTRATOR_URL/auth/login"
```

Ожидаемый ответ:

```json
{"authenticated":true}
```

## 2. Получение текущих настроек

```bash
curl -fsS \
  -b "$COOKIE_FILE" \
  "$ORCHESTRATOR_URL/api/settings" \
  -o settings.json
```

Endpoint возвращает полный публичный документ настроек:

```json
{
  "pollIntervalSeconds": 3,
  "timezone": "Europe/Moscow",
  "groups": [
    {
      "id": "storj01",
      "name": "STORJ01"
    }
  ],
  "nodes": [
    {
      "id": "storj085",
      "name": "STORJ085",
      "url": "http://192.168.200.185:14005",
      "apiKeyConfigured": true,
      "groupId": "storj01",
      "enabled": true
    }
  ],
  "schedules": []
}
```

Посмотреть идентификаторы существующих физических дисков:

```bash
jq -r '.groups[] | [.id, .name] | @tsv' settings.json
```

### Как сохраняются ключи существующих нод

`GET /api/settings` никогда не возвращает сохранённые multinode API keys.
Вместо этого у существующей ноды будет `"apiKeyConfigured": true`, а поле
`apiKey` будет отсутствовать.

Если при `PUT /api/settings` существующая нода передана с прежним `id` и пустым
либо отсутствующим `apiKey`, оркестратор подставит уже сохранённый в SQLite
ключ. Поэтому при импорте нельзя менять или удалять идентификаторы существующих
нод.

Поскольку секретные ключи не возвращаются, `settings.json` не является полной
резервной копией базы оркестратора.

## 3. Подготовка новых нод

Создайте `new-nodes.json` с JSON-массивом:

```json
[
  {
    "name": "STORJ201",
    "url": "http://192.168.200.201:14005",
    "apiKey": "MULTINODE_KEY_FOR_STORJ201",
    "groupId": "storj01",
    "enabled": true
  },
  {
    "name": "STORJ202",
    "url": "http://192.168.200.202:14005",
    "apiKey": "MULTINODE_KEY_FOR_STORJ202",
    "groupId": "storj01",
    "enabled": true
  }
]
```

Для каждой новой ноды:

- `name` не может быть пустым;
- `url` — адрес dashboard ноды, обычно с портом `14005`;
- `apiKey` — выданный нодой multinode key в формате padded URL-safe Base64;
- `groupId` — `id` существующей группы физического диска; вместо него можно
  передать `disk` с названием диска;
- `enabled` определяет, будет ли оркестратор опрашивать и запускать ноду.

Поле `id` у новой ноды можно не указывать. Оркестратор сгенерирует его и вернёт
в ответе на успешный `PUT`.

Файлы, создаваемые на следующих шагах, содержат multinode keys. Ограничьте
доступ к ним до заполнения или генерации:

```bash
chmod 600 new-nodes.json
```

## 4. Формирование нового документа настроек

Добавьте новый массив нод, не меняя остальные настройки:

```bash
jq -s '
  .[0] as $settings |
  .[1] as $newNodes |
  $settings |
  .nodes += $newNodes
' settings.json new-nodes.json > settings-updated.json

chmod 600 settings-updated.json
```

Перед отправкой проверьте итоговый список нод:

```bash
jq '.nodes[] | {
  id,
  name,
  url,
  groupId,
  enabled,
  apiKeyConfigured
}' settings-updated.json
```

Убедитесь также, что группы дисков и расписания остались на месте:

```bash
jq '{groups, schedules, nodeCount: (.nodes | length)}' settings-updated.json
```

## 5. Сохранение через `PUT /api/settings`

```bash
curl -fsS \
  -b "$COOKIE_FILE" \
  -X PUT \
  -H 'Content-Type: application/json' \
  -H 'X-Orchestrator-Request: 1' \
  --data-binary @settings-updated.json \
  "$ORCHESTRATOR_URL/api/settings" |
  jq .
```

Ответом будет сохранённый публичный документ настроек. В нём появятся
сгенерированные идентификаторы и `apiKeyConfigured: true` для новых нод, но
сами ключи возвращены не будут.

До сохранения оркестратор проверяет весь документ. В частности, будут
отклонены:

- повторяющиеся идентификаторы или dashboard-адреса нод;
- ссылки на несуществующие группы физических дисков;
- некорректные dashboard URL;
- отсутствующие или некорректные multinode keys;
- расписания, ссылающиеся на неизвестные диски или ноды;
- удаление ноды, на которую ещё ссылается активная очередь оркестратора.

При ошибке проверки существующие настройки не изменяются. Размер тела запроса
ограничен 1 МиБ, чего достаточно для нескольких сотен нод.

## Правила безопасного использования

1. Не отправляйте только `{ "nodes": [...] }`. Это `PUT`, а не `PATCH`:
   отсутствующие разделы не будут объединены с сохранёнными настройками.
2. Оставляйте каждую существующую ноду и её исходный `id`. По нему сервер
   находит и сохраняет скрытый API key.
3. Для каждой новой ноды передавайте настоящий `apiKey`.
4. Используйте HTTPS или доверенную частную сеть. В запросах передаются пароль
   оркестратора и multinode keys новых нод.
5. Не добавляйте `new-nodes.json` и `settings-updated.json` в Git. После
   проверки импорта удалите временные файлы.

Повторный запуск того же импорта не создаст молча дубликаты: сервер отклонит
повторяющиеся dashboard-адреса. Для следующей партии сначала получите новый
`settings.json` из оркестратора и повторите процедуру.
